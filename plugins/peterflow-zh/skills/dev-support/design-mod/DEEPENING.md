# 按依赖加深模块

几个浅模块共同完成一项行为时，先画出调用方、依赖以及拟保留的公开入口。用[共同词汇](SKILL.md)说明新接口替调用方承担哪项责任。再按依赖选择验证方法。

| 依赖 | 接缝与测试 |
| --- | --- |
| 进程内计算或内存状态 | 把属于同一行为的逻辑收进模块，直接通过新接口测试结果。纯计算可以保留为普通函数。 |
| 有本地替身的依赖 | 例如用 PGlite 代替 PostgreSQL，或用内存文件系统。让测试带着替身调用模块的公开入口，替换位置可留在实现内部。说明替身覆盖了哪些语义。 |
| 自己维护的远程服务 | 在确实要替换传输的地方定义端口，即模块需要的接口。业务判断由深模块负责，生产适配器使用 HTTP、gRPC 或队列，测试适配器在内存中提供响应。 |
| 无法控制的第三方服务 | 将模块需要的第三方行为收在一个可注入的端口，例如支付授权。用模拟适配器提供成功、拒绝或超时等真实相关的结果，通过模块接口验证业务行为。 |

先说清生产实现和测试替身各自服务哪个真实调用，再决定是否引入适配器。模块内部需要替换某个依赖时，把接缝留在内部，公开接口仍只表达调用方需要完成的事。

## 迁移行为测试

先列出旧测试保护的可观察行为，包括失败语义。通过新接口覆盖这些行为后，删除只重复验证旧转发步骤的测试，保留仍有独立价值的用例。用一次内部重构检查测试边界：如果公开行为未变，测试却必须跟着内部调用次序一起改，重新检查它跨过了哪条接缝。
