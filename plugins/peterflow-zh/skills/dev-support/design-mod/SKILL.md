# 模块与接口设计

让调用方通过小接口使用完整的行为，让维护者能在一处理解、修改和验证一条规则。讨论具体代码时，从一个真实调用开始，看调用者为了做成这件事究竟要知道什么。

## 共用词汇

| 术语 | 在设计中指什么 |
| --- | --- |
| 模块（module） | 拥有接口和实现的一段功能。函数、类、包乃至贯穿多层的一项业务功能，都可以作为模块讨论。 |
| 接口（interface） | 调用方正确使用模块所需的全部知识，包括签名、约束、顺序、错误语义、必要配置和性能特征。 |
| 实现（implementation） | 模块内部完成行为的代码。调用方可以通过接口使用它，内部可以有多个协作部分。 |
| 深度（depth） | 调用方或测试每掌握一份接口知识，能用到多少行为。小接口封装丰富行为的模块很深；使用接口几乎要理解整个实现的模块很浅。代码行数无法衡量深度。 |
| 接缝（seam） | 可以在一处替换行为、同时保持使用该行为的代码不动的位置。先决定接缝放在哪里，再讨论背后放什么实现。 |
| 适配器（adapter） | 在接缝处满足接口的具体实现。数据库存储和内存存储都可充当适配器，两者内部的代码量可以相差很大。 |
| 调用收益（leverage） | 同一份实现为多少调用方和测试承担了多少工作。例如，所有入口都能复用同一条计价规则。 |
| 变更局部性（locality） | 同一知识、变更、缺陷修复和验证集中在什么地方。例如，调整折扣顺序只需改计价模块一处。 |

描述架构时统一用这些词。描述业务时沿用项目的领域词汇和代码标识。用“接缝”说明行为替换的位置，可以避免与领域模型中的“限界上下文”混淆。

## 判断模块是否值得保留或加深

- **删除测试。** 设想删掉这个模块，再沿原调用走一遍。若连同它一起消失的只有转发步骤，可以考虑简化。若多个调用方都得重新实现排序、错误处理或业务规则，说明这个模块封装了有价值的知识。
- **接口是测试入口。** 让调用方和行为测试通过同一外部接缝。若测试总要穿过接口去操作内部对象，检查接口是否放对了地方。实现内部仍可有私有接缝，供内部协作或测试使用。
- **用真实差异判断接缝。** 只有一种实际适配器时，可替换性仍是假设。生产传输和确有需要的测试替身是两种真实用途。普通函数或具体类型已经够用时就沿用。
- **缩小调用方要学的东西。** 哪些方法每次都得按同一顺序调用？哪些参数可由模块自己决定？把这样的知识收进去，并用同一个调用示例核对新接口是否更容易用。

例如，折扣计算可直接返回金额，测试给定购物车即可断言结果。下单需要调用支付网关时，可由调用处传入网关，把真实扣款与可控的测试响应放在同一接缝。两种做法分别解决了一个具体的测试困难。
