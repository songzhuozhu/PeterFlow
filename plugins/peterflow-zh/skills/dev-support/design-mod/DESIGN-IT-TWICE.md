# 设计两次

当用户希望为一个已选问题探索不同接口时使用。沿用 Ousterhout 的“设计两次”方法：先让不同约束分别导出方案，再用相同的调用场景比较。普通接口问题可直接用[设计原则](SKILL.md)判断。

## 说明问题

先让用户看到接口必须满足的约束、[依赖类型](DEEPENING.md)和一小段实际调用示意。示意代码用于说明问题，给各方案保留改变接口形状的空间。

## 独立形成方案

Matt 原版采用至少三个全新上下文的子 Agent 并行设计。在宿主支持且当前授权允许时，给每位执行者一份可独立阅读的简报，写明相关文件、调用、耦合、依赖类型、接缝后要封装的行为，以及项目领域词汇。为它们分配不同的优化目标：

1. **最小接口。** 尝试用一到三个入口覆盖主要行为，让每个入口承担完整责任。
2. **多种用法。** 从已知场景出发探索更灵活的接口，标出为灵活性增加的调用成本。
3. **最常见的调用。** 让主要调用方最容易写对，再说明少数用法的代价。
4. **跨接缝的依赖。** 如果远程传输是主要约束，可另给一个方案探索端口和适配器。

每个方案交付接口形状（类型、方法、参数、约束、顺序和错误）、同一场景的调用示例、封装的实现知识、依赖及适配器策略，以及调用收益和代价。宿主无法委派时，可在当前会话按不同约束分别推演，并说明方案出自同一上下文。

## 比较并推荐

依次展示方案的调用示例，再比较模块深度、变更局部性和接缝位置。指出哪一个最适合当前调用方，并说明决定性的约束。若两种设计各有可取之处，给出组合后的具体接口和调用示例。
