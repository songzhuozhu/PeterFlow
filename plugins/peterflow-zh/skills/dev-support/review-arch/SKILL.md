# 架构巡检

用户点名调用或明确要求做架构巡检时使用。目标是找到值得投入的重构，让调用方用较少的接口知识完成更多工作，让维护者容易定位修改位置，并能通过实际入口验证行为。

## 1. 确定范围，查找候选

用户给了模块、子系统或具体痛点，就沿这条线查。范围开放时，先看一小段 Git 历史，例如用 `git log -n 30 --oneline --name-only` 找近期反复变动的区域。没有明显热点再扩大范围。没有提交历史时，从一个真实入口及其调用和测试入手。提交频繁只决定先看哪里，建议本身需要代码证据。

先读项目已有的领域词汇表（如 `GLOSSARY.md`）和范围内的架构决策记录（ADR，常见于 `docs/adr/`），沿用项目的代码导航约定。已安装 `design-mod` 时，使用它的共同词汇和判断方法。单独安装巡检包时，按下面三点走读。

- **模块、接口与实现**。接口包括调用方必须知道的参数、顺序、约束和错误语义。接口越小、能可靠使用的行为越多，模块越深。接口几乎暴露了全部实现细节时，模块很浅。
- **接缝与适配器**。接缝是可以替换行为的位置，适配器是在该处满足接口的具体实现。先找真实的变化，例如生产传输和测试替身各有用途，再考虑引入可替换接口。
- **调用收益与变更局部性**。观察多少个调用方可以省去同一段知识，以及一次规则变更究竟要改几处。做“删除测试”：设想删掉一层，若复杂度随之消失，它可能只在转发；若复杂度回到多个调用方，该层正在封装有用的行为。

宿主支持且当前授权允许委派时，用一个新上下文的子 Agent 走读选定范围，把范围、术语和相关决策交给它。单独执行时按同样方法走读。沿一个真实调用或变更追下去，特别留意理解一个概念要跨哪些文件、哪些内部步骤泄漏到调用方、哪些测试覆盖了纯函数却漏掉实际调用中的错误，以及哪些行为很难从接口验证。

## 2. 用 HTML 呈现候选

按[报告指南](HTML-REPORT.md)写一份中文 HTML。用系统临时目录（如 `tempfile.gettempdir()`），每次生成独立的 `architecture-review-<时间戳>.html`。在宿主支持时为用户打开报告，并提供实际绝对路径。

每项候选给出相关文件和调用证据、当前问题、改造方向、调用方和测试会得到的具体收益，以及并排的改造前后图。推荐程度用“强烈推荐”“值得探索”“推测待证”。用项目术语描述业务，用上述设计概念说明结构。如果候选与已有 ADR 冲突，指出决策编号，以及什么新证据值得重开讨论。

结尾选一个最值得先处理的候选并说明原因。没有足够证据时，如实说明检查范围和结果。报告阶段讲清方向，具体接口留到用户选定候选后再设计。交付报告后问用户“你想先深入讨论哪一项？”

## 3. 深入选中的候选

一次讨论一个影响设计的决定。沿真实调用逐个厘清约束、依赖、接缝的位置、由模块隐藏的步骤，以及哪些测试应保留、替换或移到公开入口。已安装配套技能时，用 `grilling` 引导追问，用 `domain-modeling` 维护领域词汇和决策。单独安装时直接与用户走完这些问题。

新概念或词义经用户确认，且本次允许维护词汇表时，写回已有的 `GLOSSARY.md`，首次需要时再创建。用户因长期约束拒绝候选，可询问是否将理由记为 ADR，供下次巡检参考。用户想探索不同接口时，使用 `design-mod` 的“设计两次”指南。若仅安装了巡检包，分别从最小接口、已知的不同用法和最常见调用出发提出方案，再用同一个调用示例比较收益、改动范围和测试成本。实施重构沿用用户对该项工作的授权。
