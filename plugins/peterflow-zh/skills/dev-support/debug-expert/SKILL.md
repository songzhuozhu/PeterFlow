# Debug 专家

先建立一个能对**用户报告的原故障**判对错的反馈循环。按以下六步排查，跳过某一步时说明理由。按项目导航约定查阅相关代码、已有术语表、设计决定和适用规范。命令通过环境变量使用凭据，展示日志或采样前脱敏，只保留解释现象所需的行。

## 1. 建立反馈循环

选一个能反复执行的入口：优先复用失败测试，也可用实际 API、带固定输入的 CLI 或界面操作。缺少现成入口时，可以回放脱敏记录，搭最小驱动，或用生成输入、版本二分、同输入的新旧对照找出触发条件。需要人工操作时，复制对应平台的模板并替换示例步骤，由操作者完成登录，只回传脱敏观察结果。

- macOS / Linux：在终端用 `bash ./hitl-loop.template.sh` 运行 [Bash 模板](scripts/hitl-loop.template.sh)。
- Windows：在 PowerShell 中用 `.\hitl-loop.template.ps1` 运行 [PowerShell 模板](scripts/hitl-loop.template.ps1)。

从原场景实际运行一次，留下入口、条件、输入、预期和失败输出。断言对准具体错误值、错误类型或耗时。固定影响结果的时间、随机种子、数据与环境，尽量缩短一轮耗时。偶发问题先记录失败次数和总次数，再寻找能提高复现率且仍触发同一现象的条件。性能回退先在同一负载下测量或剖析，保留可比较的基线。

没有取得原故障的失败信号时，在这一步说明试过什么、还缺什么。可继续只读追踪入口以建立复现，或索取脱敏样本、必要环境和临时观测授权；根因保持待确认。

## 2. 复现并缩小

同一输入从一个入口成功、另一个入口失败时，分别重放两条路径。在对应的调用上比较输入、状态和返回值，找到第一次出现差异的地方，再验证这个差异是否造成原故障。

保存最初的用户场景，另外缩小复现。每次只去掉一项输入、调用、配置或步骤，重跑同一断言；若原症状消失，把这个触发条件放回。能说明剩下哪些条件维持同一失败，才用缩小后的复现做实验。单次调用和同进程连续调用须按实际故障区分。

## 3. 提出可证伪的假设

对疑难故障先列出 3–5 个有依据的候选原因，按证据排序，并在实验前简短说明。每个原因都要给出预测：“如果原因是 X，只改变 Y，原症状应该怎样变化？” 用户掌握的部署或环境事实可以改变排序，已获授权的实验可直接进行。

## 4. 用实验区分原因

挑最能区分候选解释的预测，一次改变一个变量，比较预期与观察。优先用断点或交互检查；需要临时日志时，只在能区分原因的边界加观测，并使用本次唯一标记。性能问题用同条件测量、剖析或二分定位。线上观测或外部状态变更须在授权范围内。

根因结论写清触发条件、产生错误的机制、支持预测的观察，以及这些观察排除了哪个竞争解释。仍有同样能解释现象的原因，就继续区分或如实报告未决。**只要求诊断时，在这里交付证据和修复建议，清理本次临时观测。**

## 5. 修复并回归

获准修复后，在能经过真实故障调用链的入口，把最小复现固化为回归测试，已有合适用例直接复用。先在修前版本亲眼看到它因原症状失败，再做最小修复，用同一输入和断言观察通过。若用故障注入建立失败基线，先与原副本比较，确认注入确已生效，并注明它能证明的范围。缺合适的自动化入口时，说明覆盖缺口，保留可执行的原场景检查。

回到第 1 步保存的**未缩小的用户场景**，按原入口、数据与调用顺序再跑一次，核对原症状及受影响行为。偶发故障报告修前、修后同条件下的失败次数与总次数；性能回退报告同负载的前后测量。相邻问题修好而原断言仍失败时，原故障保持未解决。

## 6. 清理并交付

按标记移除本次临时日志，清理临时驱动，保留有用的复现、回归和用户已有资料。交付根因证据、最小修改、回归结果、原场景复验结果和未验证范围。沿用原任务或资料；短结论可留在会话。已授权提交或创建 PR 时，把根因写入对应说明，诊断本身不触发 Git 写操作。
