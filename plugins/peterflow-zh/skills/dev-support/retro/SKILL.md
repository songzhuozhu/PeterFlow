# 会话复盘

用户点名 `$retro` 后，复盘这次开发中 Agent 遇到的阻碍，提出能让下次工作更顺利的环境改进。

## 复盘步骤

1. 已安装 `writing-for-agents` 时，沿用它写 Agent 指令的方法。单装本技能时，用下文的文件分工判断建议放在哪里。
2. 读用户指定会话的一手材料。必要时定位那次会话的本机记录，看用户当时纠正了什么、Agent 执行了哪条命令、实际输出是什么。未指定就用当前会话。
3. 顺着事件，从下面七个方向选相关的查。对照现在的入口，确认当时的问题今天是否还会发生。
4. 按影响从大到小给出候选。每项指出事件和证据、最小改动、如何验证。代价影响选择时再说明。原因还没查实时，标明哪些是推测。

## 七个排查方向

- **导航。** 找文件绕路时，沿当时的路径走一遍。是入口难找，还是两个文件间有隐含依赖？若文档已经存在，先看在读者原本会去的地方加一条指引能否解决。
- **自动检查。** 错误通过了日常检查，或项目缺少自动执行检查的入口时，先读项目自己的 lint、类型检查、测试命令及相关 CI 配置。已有检查可能没接上，也可能失败后入口仍返回成功。必要时在隔离副本重放原错误。PeterFlow 将缺少钩子或 CI 作为调查线索，列为改进前要说清它能挡住这次会话中的哪一步。
- **编码规范。** 评审漏掉违规时，先判断工具能否稳定识别。禁用 API、导入方式、文件位置等机械规则，优先接到成本最低的现有 linter、提交钩子或 CI。跨文件一致性、是否符合周边代码风格等判断，才去查规范里哪条需要澄清、增补或移除。
- **常驻指令。** 项目或用户级 `AGENTS.md`、`CLAUDE.md` 太长并妨碍工作时，查看造成负担的段落。能自动执行的交给检查，已确认的判断规则归到规范，偶尔用的操作细节归到按需文档。常驻处只需说明何时、去哪里找。只查看与本次复盘有关的范围。
- **工具成本。** 一次 CLI 或 MCP 调用输出很多、真正用到的却很少时，对照实参和结果。找出能直接定位的文件、过滤条件或可复用的上次结果，再比较省掉了哪次调用或哪段输出。
- **不起作用的指令。** 常驻资料反复扩写时，考虑删掉这句话会改变 Agent 的哪一步。用实际会话判断。例如同一规则已由日常检查强制执行，再写一遍泛泛提醒是否有额外作用？一时看不出作用时，先保留疑问。
- **信息获取。** 缺少关键信息导致误判时，指出缺的是哪条证据，以及当时怎样才能看到。例如让开发服务日志可供查阅，或为相关服务提供必要的只读查询。涉及新增权限时只提出所需范围。

## 实现、评审和资料放在哪里

实现者同时要探索代码、编写和调试，上下文容易被占满。评审者通常从已有差异出发，更适合集中核对需要判断的规则。Matt 据此把规范检查放在评审阶段。PeterFlow 的开发与评审共享已确认的 `standards/`，实现时按当前改动查相关条目，评审时再对照差异核验。

- `AGENTS.md`、`CLAUDE.md` 每次都会占用上下文，适合放简短的导航指引。
- 编码规范承载需要判断的约定。Matt 以超过千行的 `CODING_STANDARDS.md` 为拆分示例。PeterFlow 默认沿用 `.peterflow/standards/` 的现有入口，按检索困难决定是否拆分。新增或改变规则语义需要已确认的依据。
- 判断一条经验值不值得留，可以问：下一个人只看当前代码、测试和文档，会不会重犯这个错误，或者还得重查一遍？已有出处就给出入口。确有遗漏时，只建议把难以重建的原因、例外或排除过的办法补回读者平时会查的资料。
- 文档适合按需查阅的细节。先找已有说明，再决定是否另写。需要反复执行的一类任务可以做成 Skill，描述写清调用时机，手动命令留给用户点名。

## PeterFlow 的交付约定

已经修好的问题，给出当前证据即可。没有仍值得做的改进，可以直接这样回答。默认在会话中报告。用户要求留档时沿用原资料位置，新研发记录按需放到 `.peterflow/specs/原主题/`。

复盘交付改进建议。值得作为团队规则保留的，注明评审或会话出处，建议用 `maintain-standards draft` 起草 L2 候选。负责人采纳后才进入现行规范。用户要求落实工具或检查改进时可交给 `implement`，操作说明和经验就地更新。单独使用本 Skill 也能完成复盘。
