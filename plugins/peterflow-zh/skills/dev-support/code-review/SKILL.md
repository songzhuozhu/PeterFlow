# 代码评审

交付两个独立结论：**规范符合性**和**需求实现**。先明确本次看哪份代码、依据哪些规则和目标，再沿真实调用路径取证。小改动由同一人完成两方面即可。

## 固定本次输入

按项目导航约定定位代码，沿用用户指定的范围。只有比较对象不清且会改变结论时才询问。

- **提交或分支**：把两端引用解析为确定的 SHA。比较两个版本时用 `git diff A B`；审分支相对共同祖先引入的变化时用 `git diff A...B`。记录实际比较关系和涉及的路径。差异为空，报告这两个版本之间没有待评改动。
- **未提交改动**：看 `git status --short --untracked-files=all`，在相关路径分别核对 `git diff --cached`、`git diff`，并打开范围内的未跟踪文件。只审暂存内容时从索引读取，例如 `git show :路径`；审整组改动时以实际工作树内容判断最终行为。已有无关修改留在范围外。
- **文件现状**：无 Git、无 HEAD 或缺少可信前态时，仍可审指定文件。注明当前版本，不推断缺陷何时引入。评审需要交接或稍后复用时，保留相关文件快照或内容摘要；未提交内容不能只靠 HEAD 标识。

## 分别取证

| 评审轴 | 依据与判断 |
| --- | --- |
| **规范符合性** | 沿用户或项目的现行入口（默认 `.peterflow/standards/`），从总索引（L3）选适用的 L0 通则和 L1 专题。涉及产品行为时，按实际调用方和功能索引查已采纳的 L2 条款。用现行条款的范围、例外和代码位置判断违规，说明触发场景和影响。候选、备份以及一次测试结果都不能自行确立规则。 |
| **需求实现** | 从用户要求、验收条件或已有规格取出应观察到的行为。从改动处追到调用方或用户入口，用能区分对错的输入核对实际结果。检查遗漏、边界错误和超范围行为，排除已明确留待后续的目标。按需运行最小验证，注明哪些结果是实测、哪些来自源码阅读。 |

同一缺陷可能影响两轴。各自说明依据，共用一条发现和修正方向。某轴缺少依据时，说明具体哪部分无法判断，继续完成另一轴。已有用户要求足以作为需求依据，无需先配置 Issue 平台。

需要独立视角且宿主支持时，两位只读评审者分别从新上下文出发，读取同一份固定代码和各自适用的依据，独立形成结论再汇总。任何一方读到不同版本，先核对受影响范围再采用其结论。

## 收尾与复审

分别回答“是否符合规范”“是否满足需求”，说明覆盖范围和判断依据。有确认问题时给出位置、触发条件、实际影响与修正方向；无确认问题时说明已经核对的部分。保留未覆盖项或缺失证据，即使另一轴已通过。

默认只报告。获准修复时保留原发现和触发条件。代码或依据在审查中、修复后发生变化，比较本次输入与原输入，沿受影响入口复核原问题和相邻边界。明确哪些发现已关闭、哪些仍成立、哪些是新发现。仅按请求留档，不自动暂存、提交或推送，也不把本 Skill 加为重型主线内部评审的额外关卡。
