# PeterFlow 流程与场景

先看用户要拿到什么，再从已有材料能支持的那一步开始。

## 从需求到交付

| 当前工作 | 从哪里开始 |
| --- | --- |
| 小改动，目标和验收清楚 | `$plan` 给出短计划，`$implement` 实施并验证。已有可执行计划就从实施开始。 |
| 多项任务有依赖，可在普通实施流程中推进 | 方案明确后用 `$tasks` 按阶段拆任务，再用 `$implement` 接续就绪任务。已有清单时核对依赖即可。 |
| 需要把工作拆给独立上下文，分单元实施、评审、测试和累计验收 | `$plan` 明确方案，`$tasks-pro` 拆独立单元，`$implement-pro` 执行。清单已有对应范围、依赖和验收时，可从重型实施接起。它自带内部评审和测试。 |

跨会话本身不决定任务档位。选择重型流程时要看是否需要独立执行单元，以及宿主能否提供独立执行者。

## 从问题选入口

| 用户想解决什么 | 推荐入口 |
| --- | --- |
| 动手前核对资料，担心照方案会做错或漏验 | `$analyze` 对照需求、方案、任务及适用依据，说明具体后果。 |
| 已经有代码差异，要查规范和需求是否满足 | `$code-review` 评审指定的改动范围。 |
| 到了收尾阶段，不确定还有什么没交付或没验 | `$converge` 对照目标、当前实现和证据，把缺口补回原计划或任务。 |
| 功能进行中，用户推翻或更改了之前的决定 | `$feature-retcon` 评估新决定影响的层级，按授权追平需求、任务、代码和验证。原目标中的普通遗漏可沿原任务继续。 |
| 结果异常，需要定位故障或性能回退的根因 | `$debug-expert` 从失败信号追到根因。根因和改法已经明确时可直接实施。 |
| 已选定模块，想比较接口、职责和测试方式 | `$design-mod` 讨论具体的模块设计。 |
| 想从整个代码库找出最值得改的结构 | `$review-arch` 巡检候选，再深入用户选中的模块。 |
| 有一个技术事实要核实，或几种技术方案需要比较 | `$research` 按目标版本和环境核对一手资料，给出结论与证据缺口。 |
| 要系统学会某个主题 | `$learn` 逐节教学，也可先讨论 roadmap，确认后一次生成全部课件。 |
| 写给人的中文说明需要讲清楚或润色 | `$shuorenhua` 按指定读者和范围处理。用户单发“说人话”时重讲上一条。 |
| 写给 Agent 的 Skill、AGENTS.md 或其他指令需要改 | `$writing-for-agents` 明确触发条件、阅读路径和完成条件。 |
| 想从一次真实会话找出下次可以改进什么 | `$retro` 在用户点名时复盘，交付改进候选。选定的工具或检查改动可交给实施流程。 |
| 要建规范库、起草候选、采纳规则或检查规则过时与冲突 | `$maintain-standards` 按相应动作维护共享规范。 |

## 在哪一个会话继续

- 当前会话已有这项工作的依据和授权，可以直接从原计划或任务继续。阶段变化本身不要求重开会话。
- 若某一步需要独立视角，例如重型 Phase 的评审和测试，按该单元的角色协议交付必要输入，由独立执行者回报结果。主会话保留决策上下文，是否派工取决于当前任务范围和宿主能力。
- 用户要**在当前会话同步某个功能的开发上下文**，或单独说“更新下 quickstart”，选 `$quickstart`。它核对功能接手页，发现进度过时就追到当前接手点并回写。
- 用户明确要**把上下文交给另一个新会话**，选 `$context-handoff`。用户显式调用后会准备交接包，新会话首轮接收、回执并等待下一条指令。向已获准的子任务同步必要上下文也可借用它；派工由原任务流程负责。
