# 编写面向 Agent 的文档

Skill、`AGENTS.md`、`CLAUDE.md`，以及它们引用的资料，都可以用同一套写法。文档要让 Agent 每次都按可靠的过程工作；具体产出随任务变化。

编写 Skill 时，另读 [Skill 的调用机制](SKILL-MECHANICS.md)，确定元数据、调用方式以及是否需要导航型 Skill。

## 上下文指引

**上下文指引**告诉 Agent 在什么情况下去读上下文之外的哪份材料。Skill 的 `description`、`AGENTS.md` 中指向操作手册的一行文字，都是指引。措辞决定了材料会在何时被读到。必读材料时常被跳过，先改清触发条件；仍然漏读，再考虑把内容放回正文。

指引要说明材料的用途，并列出会用到它的不同情形。每种情形都应对应一条真正不同的执行路径。常驻上下文的每个词在每轮对话中都有成本，写这类指引尤其要精简。

- **把引导词放在开头。** Agent 正是在读到指引时判断要不要调用。
- **每个分支只写一个触发条件。** 合并同义说法，保留真正会改变执行路径的区别。
- **删掉重复的身份说明。** 正文已有的自我介绍无须再塞进指引。

## 两种负担

- **上下文负担**由 Agent 承担。`AGENTS.md` 中的一行说明、Skill 的描述等常驻材料，每轮都占用上下文和注意力，即使这轮完全用不到。
- **认知负担**由人承担。没有指引时，人就要记得有哪些资料、何时该用哪一份。需要人作判断的地方，值得付出这份成本，以便人保留选择权。

按指引才读取的资料，平时只占一条指引的篇幅。连指引都省掉，就完全依赖人主动想起来。

## 信息层级

文档里有按顺序执行的**步骤**，也有按需查阅的**参考**，包括定义、规则和事实。一份文档可以全是步骤，全是并列的评审规则，也可以两者兼有。按 Agent 多快需要看到这段信息，选择放置位置。

1. **正文中的步骤。** 直接写出该做什么、先做什么。
2. **正文中的参考。** 需要时就近查阅。若几条规则同等重要，并列放在一起很合理。
3. **单独的参考资料。** 从入口移出，通过带条件的指引读取。资料可以是同目录下的文件，也可以是多份文档都能引用的外部来源。

全部留在入口，步骤容易被淹没；移出去太多，执行者又会漏掉必需信息。用分支判断最直观：各条路径都需要的内容留在正文，只有部分路径需要的内容按需展开。这就是**渐进披露**。它首先保护信息层级，也能节省上下文。藏在大段参考里的操作步骤容易被忽略，使执行结果时好时坏。

在同一份文件里，把一个概念的定义、规则和限制放在同一标题下，让读者一次就能看全。重复是同一意思写了几遍；分散则是一个意思要拼好几段才能读懂。

即使每句话都有用、没有一句重复，文档也可能过长。注意力会被稀释，维护者还要持续判断每行是否仍然适用。把参考移到按需入口，或按分支、执行阶段拆开，让每次执行只携带当前需要的部分。

## 步骤与完成条件

每一步都要有**完成条件**，让 Agent 知道何时可以继续。写条件时看两个方面。

- **是否清楚。** 执行者能分辨完成和未完成吗？“已充分理解”很难核对。后面的步骤已经摆在眼前，Agent 容易急着往下走。先把当前步骤的边界写具体，这是成本最低的修正。只有确实观察到抢跑，且完成条件本身很难再写清时，才把后面的步骤隔开。要真正隔开，需要交接或派给新的子 Agent；同一上下文中再调用一次，后续步骤仍然可见。
- **要求做到什么程度。** “列出变更”允许执行者交一份不完整的清单；“逐一说明每个已修改模型的变更”要求实际查全。条件的措辞决定执行者会下多少查证功夫，无须把每次查找都列成步骤。纯参考文档也能要求“逐条应用所有适用规则”。

有力的完成条件既能核查，也能覆盖本步的全部目标。

## 何时拆分

多一份文档，就要付出上下文负担或人的认知负担。拆分应带来明确收益。

- **按执行顺序拆。** 当后面的工作持续诱使 Agent 草草结束当前步骤，可以让后面的步骤在真正交接后才出现。反过来，合并原本分开的流程，会让后续步骤提前可见，增加过早结束的机会。
- **按调用方式拆。** Skill 有单独的判断方法，见 [Skill 的调用机制](SKILL-MECHANICS.md#按调用方式拆分)。

## 引导词

**引导词**是模型已经熟悉、又能简洁表达一类行为的概念，如“教训”“战争迷雾”或“曳光弹”。在不同位置复用同一个词，各处的用法会共同说明它的含义，无须反复写整句解释。自造词也能用，但要先支付定义成本。优先考虑已有术语。

引导词在两个地方起作用。在正文中，它让执行者稳定地想到同一种做法；在并列的评审规则里，它提醒执行者关注某一类问题。在指引中，如果提示词、文档和代码使用同一术语，Agent 更容易把请求和相应资料联系起来。

留意多处重复的解释，看看是否有一个熟悉的词足以替代。例如：

- 英文里的 *tight loop* 可以概括“快速、确定、开销低”的反馈循环。
- 与其说“建立一个你相信的反馈循环”，可以说让用例在缺陷上“变红”。“红”给出了一个能观察的判定。

既节省篇幅，又让执行者更容易抓住要做什么。反复使用术语有助于建立联系，反复解释同一条规则则会增加负担。

只用否定句引导，有时反而会让被禁止的行为更显眼。读到“别想一头大象”时，人先想到的就是大象。尽量直接写目标行为，例如“注释写成一行”。确实需要明确禁止的硬边界要保留，并在旁边写明应当怎么做。

## 删减

- **每项要求有一处权威表述。** 行为改变时只需维护一个地方。多处复述既占上下文，又会因重复而夸大这条规则的重要性。可以反复用同一个引导词，避免反复定义它。
- **环境本身也是事实来源。** `package.json` 的脚本、配置文件、目录布局和命令的 `--help` 都能直接查询。在文档里重抄一遍，就要持续维护这份副本。值得记录的是查找代价高的内容，如未明文规定的惯例、约束的原因、或要付出一次失败才知道的陷阱。
- **逐行核对相关性。** 有些句子从一开始就只是泛泛的建议；另一些曾经有用，但涉及的分支已消失，或外部环境已变化。短文档需要维护的内容较少。定期从过时条目里找回仍然有效的规则。
- **逐句找出不改变行为的指令。** 判断标准取决于使用它的模型：拿掉这句，实际做法会变吗？存疑时用文档试跑一次。若没有差别，整句删除比修饰措辞更有效。“务必认真”之类引导词力度不足时，换成能引出具体行为的概念。
