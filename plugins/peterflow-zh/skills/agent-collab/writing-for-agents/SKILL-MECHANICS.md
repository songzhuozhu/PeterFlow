# Skill 的调用机制

编写 Skill 时，还要决定入口元数据、谁能发起调用、是否需要导航。通用文档写法见[面向 Agent 的文档](SKILL.md)。

## 谁来调用

按宿主设置调用方式。PeterFlow 的仅用户调用技能在 Claude Code 的 frontmatter 使用 `disable-model-invocation: true`，在 Codex 的 `agents/openai.yaml` 中设置 `policy.allow_implicit_invocation: false`。两种语言都保留可读的技能描述。

两种调用方式分别消耗 Agent 的上下文和人的注意力。

- **模型可调用。** 保留面向模型的 `description`，省略 `disable-model-invocation`。Agent 能根据任务自行选用，其他 Skill 也能引用它，用户仍可点名调用。描述作为常驻的顶层指引，用少量上下文换取可发现性，要写清不同的触发分支。内容全是参考资料的 Skill 也可以采用这种方式，为多个调用方维护一份共同资料。
- **仅用户调用。** 在采用原版这套元数据约定的宿主中，设置 `disable-model-invocation: true`，将 `description` 写成给人看的一行摘要，省去触发词列表。模型无法自行选用，其他 Skill 也不能发起调用。这样可以省去常驻上下文，代价是用户要记住它、在需要时主动点名。

需要 Agent 自行发现、或需要其他 Skill 调用时，才值得支付常驻描述的成本。始终靠人点名的操作可以保留给人决定。

两个仅用户调用的 Skill 如果共用一份参考资料，可以把资料放进独立的普通文件，供双方引用。放在其中一个 Skill 的调用入口里，另一个无法通过调用取得它。

## 按调用方式拆分

出现独立的引导词，而且用户确实用它提出请求，或其他 Skill 确实需要独立调用这项能力时，才值得拆成一个模型可调用的 Skill。新增的常驻描述应当换来独立使用的价值。按执行顺序拆分的判断见[主文档](SKILL.md#何时拆分)。

## 导航型 Skill

当仅用户调用的 Skill 多到难以记住时，可以设置一个也由用户点名的导航入口，列出各项名称及适用时机。用户记住一个入口即可。导航能提示接下来该点哪项，最终仍由用户调用。
